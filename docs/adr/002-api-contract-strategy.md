# ADR 002: API Contract Strategy — Code-First OpenAPI with utoipa

## Status

Accepted

## Context

The PudimFinance API contract defines the interface between the Rust backend and
TypeScript consumers (web and mobile). Phase 0 established a contract-first workflow
using hand-written OpenAPI 3.1 YAML files in `api/openapi/`, with the health endpoint
as a starting point.

As the project grows through Phases 1–8, the DEV_PLAN anticipates approximately
seven or more API specifications (transactions, categories, budgets, reports,
reconciliation, receipts, price history). Maintaining these as separate hand-written
YAML files introduces several risks:

1. **Spec/code drift** — The Rust handler signatures, request types, and response
   types can silently diverge from the hand-written spec, breaking contract tests
   and generated clients.
2. **Duplication** — Schema definitions (e.g., UUID, monetary amounts, date ranges)
   must be duplicated in Rust types and YAML, increasing maintenance burden.
3. **No compile-time validation** — A typo in a YAML path or response code is not
   caught until contract tests run or clients fail.

### Alternatives Considered

| Approach | Description | Key Tradeoff |
|----------|-------------|--------------|
| **Hand-written YAML** (current) | Specs authored manually in `api/openapi/` | Full design freedom, but no type safety |
| **Code-first via utoipa** | Rust annotations generate OpenAPI at compile time | Loses "design first" workflow; Rust compiler validates spec |
| **Code-first via aide** | Alternative to utoipa with Axum integration | Smaller ecosystem, fewer features |
| **gRPC + Protobuf** | Service definitions in `.proto` files | Requires web proxy; paradigm shift from REST |

## Decision

We will use **utoipa** for code-first OpenAPI generation from Rust annotations.
The OpenAPI spec becomes a **build artifact** — generated by a dedicated binary
(`gen-openapi`) and committed to version control.

### Workflow

1. Annotate Rust handler functions with `#[utoipa::path(...)]` and request/response
   types with `#[derive(utoipa::ToSchema)]`.
2. The `ApiDoc` struct (in `backend/src/openapi.rs`) aggregates all paths and schemas
   into a single OpenAPI document.
3. A `gen-openapi` binary (`backend/src/bin/gen-openapi.rs`) outputs the spec as JSON:
   ```bash
   cargo run --bin gen-openapi > api/openapi/openapi.json
   ```
4. The committed `api/openapi/openapi.json` is the canonical contract artifact.
5. TypeScript/React Native clients use `openapi-typescript` to generate types:
   ```bash
   npm run generate-types  # runs openapi-typescript on the JSON spec
   ```

### Serving

- The main backend serves the generated spec at `GET /api-docs/openapi.json`
- Swagger UI is served at `/swagger-ui` via `utoipa-swagger-ui`

### CI Enforcement

- Backend CI runs `gen-openapi` and diffs the output against the committed spec.
  A mismatch fails the build, preventing accidental contract changes.
- Web/mobile CI runs `generate-types` and diffs generated types against committed
  versions.

## Consequences

### Positive

- **Single source of truth**: Rust types and handler signatures define the API.
  The spec cannot drift from implementation.
- **Compile-time validation**: Invalid paths, missing response codes, or type
  mismatches in utoipa annotations produce compiler errors.
- **Reduced boilerplate**: Schema definitions are written once as Rust structs;
  OpenAPI and TypeScript types are derived automatically.
- **Future-proof**: As Phase 1+ adds new handlers, adding them to the
  `ApiDoc` struct is trivial — no new YAML files needed.

### Negative

- **No "design-first" workflow**: API design happens inline with Rust code, not
  as a separate specification exercise. This can be mitigated by reviewing the
  generated spec in code review.
- **utoipa macro complexity**: Advanced OpenAPI features (discriminators, oneOf)
  can be awkward to express. For the REST resource patterns in this project
  (CRUD on accounts, transactions, budgets), utoipa's expressiveness is sufficient.
- **Compile-time overhead**: utoipa macros add some compilation time. This is
  acceptable given the project's Rust-centric workflow.

### Neutral

- **OpenAPI remains the contract format**: All downstream tooling (contract tests,
  API gateways, documentation) continues to consume standard OpenAPI 3.1.
- **Multiple API versions**: utoipa supports multiple `ApiDoc` structs for
  versioned APIs (e.g., `V1ApiDoc`, `V2ApiDoc`) — useful for Phase 6's
  deprecation strategy.
